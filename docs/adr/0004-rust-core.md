# ADR-0004: Optional Rust core with a Python fallback

- **Status:** Accepted
- **Date:** 2026-11-01

## Context
The Python encoder is readable and dependable but runs at roughly one megabyte per second, which limits
it for large corpora. A compiled core can be an order of magnitude faster, but a second
implementation is only useful if it never changes a result, and the package must keep installing
and passing its tests on machines without a Rust toolchain.

## Decision
Implement the pre-tokenizer, byte map, merge loop, and trainer in Rust (`rust/`) and expose them
through PyO3 as a separate extension module, `bpe_tokenizer_rs`, built with maturin. The Python
implementation stays the reference and the default. `BPETokenizer` accepts `backend="rust"`,
which uses the extension when it is importable and has a character table for the interpreter's
Unicode version, and otherwise falls back to Python; `tokenizer.backend` reports which is active.

The Python pre-tokenizer depends on the `re` module's `\s`, `\d`, and `\w` classes, which follow the
interpreter's Unicode database. Rather than approximate them with Rust's Unicode properties, the
Rust core uses tables generated by asking `re` itself to classify every code point
(`scripts/gen_unicode_tables.py`), one table per Unicode version. The pattern's alternatives are
reimplemented as a single left-to-right scan, including the backtracking behavior of
`\s+(?!\S)`.

## Consequences
- Identical output is a tested property: CI builds the extension and runs the parity suite, which
  fails rather than skips when the extension is missing.
- The extension is optional, so the default install and the existing CI job are unaffected.
- Supporting a new Python release with a newer Unicode database means generating one more table;
  until then that interpreter uses the Python backend.
- Two implementations must be kept in step; the parity suite is the guard.
